## 2. Research — per-position trailing profit-lock

**Сначала проверили корзинный (basket-level) trailing** — это уже было
исследовано и ОТКЛОНЕНО в предыдущей сессии (`basket_trailing_stop_research.py`,
см. part 1 хендофф): резал победителей по совокупному PnL всей корзины разом.

**Per-trade версия — другая идея**: трекать пик unrealized-профита ОДНОЙ
позиции, закрывать только её при откате. Построено:
- `src/trailing_profit_lock_sweep.py` — per-cell sweep, self-check (arm=1e9
  должен точно воспроизводить baseline), 12 активных ячеек × сетка arm_frac ×
  trail_frac.
- `src/trailing_profit_lock_combo_check.py` — портфельная проверка (все 12
  ячеек конкурируют за маржу/приоритеты, как в реальности).

**Первый прогон** (сетка 0.3-1.0 arm / 0.3-0.7 trail): нашёл выигрыш на 8/12
ячеек. **Второй прогон** (по запросу "максимальная защита профита", сетка
расширена до 0.1-1.0): 3 из 8 ячеек стали заметно туже (более ранняя защита)
без потери качества — **1h/OB** (0.5→0.1 arm), **1h/FVG** (0.3→0.1 arm),
**30m/FVG** (0.3→0.2 arm). Остальные 5 (15m/FVG, 15m/MB, 15m/OB, 30m/OB,
2h/MB) остались на исходных значениях — более тугой порог там ХУЖЕ (см.
конкретные цифры для 15m/FVG в чате: arm=0.1 роняет val_calmar с 10.21 до
0.13-6.15 — там r_target=10.0, всего 2.8% сделок доходят до полного тейка, и
ранний trailing режет именно те редкие большие победители, что формируют
весь эдж).

**Портфельный итог (финальные параметры)**: validation calmar 106.3→121.6
(+14%), holdout 68.3→82.6 (+21%), просадка ниже на каждом сплите, 0/8
отрицательных кварталов сохранено. Доходность почти не меняется — выигрыш
это снижение риска при той же прибыли.

**Живые (задеплоенные) параметры** — `tyagach/services/config.py::TRAIL_PARAMS`:
```python
TRAIL_PARAMS = {
    ("1h", "OB"):    (0.1, 0.1),
    ("30m", "OB"):   (0.7, 0.3),
    ("30m", "FVG"):  (0.2, 0.7),
    ("15m", "FVG"):  (0.5, 0.3),
    ("15m", "MB"):   (0.3, 0.5),
    ("15m", "OB"):   (0.5, 0.5),
    ("1h", "FVG"):   (0.1, 0.3),
    ("2h", "MB"):    (0.5, 0.5),
}
# выключено (не в словаре = trailing никогда не армируется):
# 2h/OB, 2h/FVG (слишком короткий expiry), 30m/MB, 1h/MB (нет устойчивого выигрыша)
```
Формат: `(arm_frac, trail_frac)` — арм при peak >= arm_frac × премии, закрытие
при откате на trail_frac от пика.

## 4. Живое подтверждение — увидели армирование в реальном времени

Позиция id=37 (15m/FVG, открыта после деплоя, премия $17.36, порог
армирования = 0.5×17.36 = **$8.68**) прямо в течение этого чата дошла до
пика **$9.42** и **армировалась** (подтверждено через `/api/v1/tyagach/positions`,
поле `trail_peak_usd`). Порог закрытия на тот момент: $9.42×0.7≈**$6.60** —
если бы откатило туда, закрылось бы автоматически с `exit_reason='trail'`.
**Не проверено, чем в итоге закрылась эта конкретная позиция** — следующая
сессия должна первым делом посмотреть её (`GET /api/v1/tyagach/positions?status=closed`
или прямой SQL по `id=37`) и другие `exit_reason='trail'` записи, накопившиеся
с этого момента.

**Побочное честное наблюдение**: позиция id=36 (та самая утренняя, разбор
которой начал всю тему) в итоге закрылась по SL (−$11.29), и её
`trail_peak_usd` в реальной БД весь день оставался **$0.00** — то есть по
настоящим рыночным котировкам пик так и не достиг уровня армирования,
несмотря на то что историческая BS-реконструкция (с замороженной entry-IV)
показывала спайк до +$3.94 в момент входа. Это разошлось с реальностью —
напоминание, что BS-approximation на исторических свечах не гарантированно
точно повторяет то, что покажут реальные рыночные котировки (тонкий
стакан/skew в конкретный момент могут отличаться).

## 5. Открытый вопрос: частота опроса цены для trailing — НЕ менять сейчас

Пользователь спросил, не редко ли проверять раз в минуту (`POLL_SECONDS=60`).
**Разобрали и решили НЕ трогать сейчас**:
- Кэш котировок (`mark_pricing._QUOTE_CACHE_TTL_S=8.0`) — реальный
  практический пол уже ~8 секунд; ускорение тика без снижения TTL кэша почти
  ничего не даст.
- `POLL_SECONDS` — глобальный тик ВСЕГО бота (сканирование зон, входы,
  обычный SL/TP-свип, equity-снапшоты), не только trailing.
- Ускорение в 6-12× — это в 6-12× больше запросов к Bybit API по каждой
  открытой позиции каждый тик — риск rate-limit.
- **Решение**: подождать неделю живой статистики по `trail`-срабатываниям,
  посмотреть, был ли хоть один случай, где гэп между 60-секундными тиками
  реально стоил денег, и по факту выбрать частоту — не менять вслепую.

## 7. Побочная ветка — Jony: тот же механизм протестирован, ОТКЛОНЁН

Пользователь спросил, помог бы такой же механизм Jony (ETH+BTC VRP-корзина,
`~/Desktop/Jony`). **Не стал слепо переносить** — сначала разобрался в
архитектуре: у Jony exit УЖЕ нормализован и проверяется каждую минуту
(`loop.py::manage_exits`, `pnl_pct_mark = (entry-mark)/entry`), но TP2 —
фиксированный одноразовый порог (0.70), без трейлинга. Гипотеза: раз опцион
теоретически может распасться до 100% (истечь бесполезным), фиксированный
порог отдаёт потенциальную прибыль — trailing мог бы дать идти дальше.

Построено (в `~/Desktop/Jony/research/`, НЕ закоммичено):
`trailing_exit_sweep.py` — векторизованный трейлинг в родной для Jony
конвенции (лучший/худший case за бар, как их же SL/TP уже считают). Self-check
прошёл. Полная сетка: PUT/CALL × с потолком tp2/без потолка × arm 0.1-0.5 ×
trail 0.2-0.7 = 80 вариантов на реальных 2 годах данных.

**Результат — однозначный отказ**: КАЖДЫЙ вариант хуже baseline и на train,
и на holdout, и по просадке (лучший из худших ~+440% holdout против базовых
+2440.5%). **Причина, отличная от уже отклонённого vol-guard**: Jony
зарабатывает на theta-распаде НЕДЕЛЬНОГО опциона (168ч) — временный откат от
пика посреди многодневного распада это шум, не разворот тезиса. Ранний выход
на этом шуме обрывает позиции, которые скорее всего продолжили бы
распадаться к профиту. Это усиливает вывод по vol-guard (тоже отклонён, 3
раунда) новым, более прямым механизмом.

**Записано в память** (`project_bot_fleet.md`) — не перетестировать без новых
данных. Скрипт не закоммичен (research-only, живой код Jony не тронут).
