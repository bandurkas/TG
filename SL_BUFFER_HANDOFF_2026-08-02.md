## Задача, которую решаем

Пользователь заметил: последние сделки Tyagach — почти сплошные SL, заподозрил
неверный расчёт стоп-лосса. Разобрался и подтвердил гипотезу количественно.

## Что нашли (уже доказано, не гипотеза)

1. **Реальные сделки**: из 31 закрытой сделки 20 (64.5%) закрылись по SL.
   Последние 6 подряд (02.08) — все bearish/CALL, все SL, пробиты одним
   трендовым движением ETH вверх через несколько bearish-зон подряд.
2. **SL-дистанция подозрительно узкая и не масштабируется по TF**: во всех
   реальных сделках ~0.15-0.35% от входа, независимо от таймфрейма (даже у
   2h/MB стоп всего 0.17%).
3. **Причина — код**: `services/signal_engine.py::scan_pending_zones()`
   считает `stop_price = zone_edge ± buf`, где
   `buf = config.BUFFER_FRAC * mid_price`, а `BUFFER_FRAC = 0.0015` (0.15%)
   — **фиксированный процент, захардкожен**, "same as options_backtest.py"
   (унаследован из другого проекта, ни разу не тюнился/не свипался за всю
   историю Tyagach — проверено по `git log -S BUFFER_FRAC`).
4. **Количественное доказательство на реальных klines**
   (`~/Desktop/Tyagach/data/eth_*.csv`): медианный диапазон ОДНОЙ свечи уже
   больше типичной SL-дистанции:
   | TF  | медианный range/свечу | наблюдаемый SL-dist в сделках |
   |-----|------------------------|--------------------------------|
   | 15m | 0.371%                 | ~0.15-0.35%                    |
   | 30m | 0.539%                 | ~0.15-0.35% (не растёт!)       |
   | 1h  | 0.764%                 | ~0.15-0.35% (не растёт!)       |
   | 2h  | 1.09-1.14%             | ~0.15-0.35% (не растёт!)       |

   95% всех 15m-свечей уже шире самого буфера (0.15%) в одиночку. Разрыв
   РАСТЁТ на старших TF, потому что буфер не масштабируется, а реальная
   волатильность — растёт. Стоп срабатывает от обычного шума одной свечи,
   а не от реального пробоя структуры.

## Решение (выбрано пользователем): TF-зависимый буфер через ATR

Вместо `buf = BUFFER_FRAC * mid_price` (константа) —
`buf = atr_mult * ATR(14)` (считается отдельно на каждом TF, причинно —
только по барам до входа, без заглядывания вперёд).

## Что уже сделано

Написан `src/sl_buffer_atr_sweep.py` (НЕ прогнан ни разу, только
синтаксически проверен `ast.parse` — OK). Построен на каркасе
`u3_solo_validation.py` (тот же per-trade → portfolio(60/20/20) →
8-квартальная робастность, что использовался для всех прошлых U1-U4
раундов) — минимальные изменения:
- `atr_series()` — Wilder-style true range, rolling mean(14), без lookahead.
- `find_entry()` — та же логика rejection-close что в проде
  (`find_rejection_entry`), но `buf_mode` параметризован: `"flat"`
  (текущее живое поведение, baseline) или `"atr"` (новое, с `atr_mult`).
- `main()` гоняет baseline + ATR mult ∈ {1.0, 1.5, 2.0, 3.0} по всем 6 живым
  парам (kind,tf) у которых есть валидированный конфиг: (OB,1h/30m/15m),
  (FVG,1h/30m/15m) — те же `CANDIDATES`, что в `u3_solo_validation.py`.
- Печатает per-split (train/val/holdout) return/maxDD/calmar + 8-квартальную
  робастность (кол-во отрицательных кварталов, mean/worst return, worst dd)
  для каждого варианта, плюс сводную таблицу в конце.

**НЕ включены в первый прогон**: MB, BB (другие zone_kind, `find_rejection_entry`-подобной
функции для них может не быть в текущем виде — проверить перед
расширением) и 2h-таймфрейм (в `CANDIDATES` его нет, только 15m/30m/1h).
